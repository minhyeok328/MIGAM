# 미감 문서 관리 정책

## 1. 목적

이 문서는 미감의 제품·데이터·추천·UX·기술·품질 문서가 서로 다른 결론을 내리지 않도록 관리하는 기준이다. 문서는 설명 자료가 아니라 향후 사람과 에이전트가 같은 결정을 재현하기 위한 계약으로 취급한다.

## 2. 문서 상태

모든 관리 대상 문서는 다음 상태 중 하나를 사용한다.

| 상태 | 의미 | 구현 근거로 사용 가능 여부 |
| --- | --- | --- |
| `DRAFT` | 확정된 대화를 구조화한 초안이며 검토가 필요함 | 불가 |
| `IN_REVIEW` | 담당자가 검토 중이며 변경 가능성이 있음 | 불가 |
| `APPROVED` | 제품 책임자가 범위와 내용을 승인함 | 가능 |
| `IMPLEMENTED` | 승인된 문서가 코드와 검증 결과에 반영됨 | 가능 |
| `DEPRECATED` | 새 결정이나 문서로 대체되어 더 이상 유효하지 않음 | 불가 |

`DRAFT` 문서가 구체적으로 보인다는 이유만으로 구현 결정을 확정해서는 안 된다. 구현에 착수하려면 관련 상위 문서가 모두 `APPROVED` 이상이어야 한다.

## 3. 필수 메타데이터

Markdown 문서는 다음 front matter를 기본으로 사용한다.

```yaml
---
title: "문서 제목"
status: DRAFT
version: "0.1.0"
last_updated: "2026-08-29"
authoritative_for:
  - "이 문서가 결정하는 범위"
related_documents:
  - "상대 경로"
---
```

- `authoritative_for`에는 다른 문서가 재정의하면 안 되는 범위를 적는다.
- `related_documents`는 실제로 존재하는 문서만 가리킨다.
- 외부 약관이나 API처럼 재확인이 필요한 문서는 본문에 확인일과 출처를 별도로 기록한다.
- 열린 결정이 있으면 `OD-###` 식별자를 본문에서 참조한다. 식별자 없는 미정·할 일 표기나 익명 빈칸은 사용하지 않는다.

## 4. 버전 규칙

문서 버전은 의미 기반 버전을 따른다.

- `MAJOR`: 기존 구현이나 하위 계약과 호환되지 않는 범위·규칙 변경
- `MINOR`: 기존 결정과 호환되는 요구사항·섹션 추가
- `PATCH`: 의미를 바꾸지 않는 설명 개선, 링크 수정, 오탈자 수정

승인 전 문서는 `0.x.y`, 최초 승인 문서는 `1.0.0`으로 올린다. 문서 버전과 향후 API 버전은 별도로 관리한다.

## 5. 문서 권한과 읽기 순서

문서의 기본 우선순위는 다음과 같다.

1. 사용자가 대화에서 명시적으로 승인한 최신 결정
2. Project Brief
3. P0 PRD
4. Domain Rules와 Data Source Policy
5. Data·Recommendation 명세
6. UX·Engineering 명세
7. API 기계 계약
8. Acceptance·Test 문서
9. Implementation·Task 문서
10. 코드 주석과 예시

같은 계층에서 충돌하면 더 구체적인 권한을 가진 문서를 따른다.

## 6. 충돌 처리

하위 문서가 상위 문서와 충돌하면 다음 순서로 처리한다.

1. 구현과 하위 문서 수정을 멈춘다.
2. `decision-register.md`에 충돌 또는 새 결정 후보를 기록한다.
3. 해당 범위의 상위 문서를 먼저 수정하고 다시 승인받는다.
4. 영향받는 하위 문서의 버전과 상태를 갱신한다.
5. 추적성 매트릭스와 테스트 기준을 마지막에 동기화한다.

충돌을 해결한다는 이유로 하위 문서가 제품 범위를 조용히 바꾸면 안 된다.

## 7. 열린 결정 관리

열린 결정은 문서 작성 자체를 막지 않는 경우 `DRAFT` 안에서 식별자로 참조한다. 다만 다음에 해당하면 관련 문서를 `APPROVED`로 바꿀 수 없다.

- 법적 사용 범위나 데이터 재배포 가능성을 바꾸는 결정
- 개인정보·인증·외부 공개 범위를 바꾸는 결정
- 실제 출처 allowlist와 이미지 이용 권리를 확정하는 결정
- 운영 비용, 배포 대상, 모니터링 도구를 확정하는 결정
- 구현 일정과 병렬 작업·리뷰 방식을 확정하는 결정

열린 결정이 해결되면 등록부의 상태를 `RESOLVED`로 바꾸고, 영향받은 문서에 결정 내용을 반영한 뒤 버전을 올린다.

## 8. 변경 검토 체크리스트

문서를 변경할 때 다음을 확인한다.

- 최신 사용자 결정과 일치하는가?
- 이 문서가 권한을 가진 범위만 다루는가?
- 다른 문서의 규칙을 중복 복사하지 않고 링크로 참조했는가?
- 폐기된 초기안이 다시 들어오지 않았는가?
- 식별자 없는 미정 표기, 빈 링크, 존재하지 않는 파일 참조가 없는가?
- 접근성·개인정보·출처·권리 조건이 약해지지 않았는가?
- 변경으로 영향을 받는 요구사항, 화면, API, 테스트 연결을 갱신했는가?

## 9. 현재 적용 범위

현재 문서 세트는 모두 `DRAFT`다. 코드 구현과 외부 배포를 승인하지 않으며, 전체 기획 대화에서 확정된 내용을 검토 가능한 형태로 정리하는 데 목적이 있다.
