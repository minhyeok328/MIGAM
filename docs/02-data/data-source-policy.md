# 미감(美感) Data Source Policy

## 1. 문서 목적과 권위 경계

이 문서는 미감이 어떤 외부 자료를 사실 근거로 받아들이고, 그 자료를 어떤 권리 경계 안에서 저장·가공·표시할 수 있는지 정한다. 수집 주기와 실패 복구는 `data-pipeline.md`, 원본값의 변환은 `normalization-rules.md`, 저장할 개념과 관계는 `data-model.md`가 정한다.

출처가 공식이라는 사실과 콘텐츠를 재사용할 수 있다는 사실은 서로 다르다. **사실 신뢰도, 접근 허용, 복제·표시 권리**를 각각 확인해야 한다.

## 2. 기본 원칙

1. 전시 상태·기간·장소·가격·예약·접근성처럼 방문 판단에 쓰는 값은 해당 사실을 책임지는 공식 출처로 확인한다.
2. 수집 편의보다 출처의 이용조건, 접근 통제, 로봇 정책, 저작권과 라이선스를 우선한다.
3. 화면에 쓰는 핵심 값은 출처, 원본 식별자 또는 URL, 확인 시각까지 추적 가능해야 한다.
4. 출처 간 충돌을 조용히 덮어쓰지 않는다. 채택값과 함께 충돌한 원본·확인 시각·판정 근거를 보존한다.
5. 확인할 수 없는 선택 방문 정보는 `UNKNOWN`으로 유지한다. 최소 품질 핵심값의 누락은 합격 처리하지 않으며, 어떤 누락값도 비공식 추정이나 생성형 해설로 채우지 않는다.
6. 데모 데이터도 운영 데이터와 같은 출처·권리 기준을 따른다.

## 3. 허용 출처 계층

실제 P0 출처 목록은 OD-003에서 승인한 [`sources.yaml`](../../sources.yaml)의 allowlist로 제한한다. allowlist 안에서도 필드별 책임 주체가 더 직접적인 출처를 우선한다.

### 3.1 allowlist 선정 원칙

P0 기관·출처 후보는 **데이터 품질**과 **반복 가능한 확보 가능성**을 공동 최우선 기준으로 평가한다. 한 기준의 장점으로 다른 기준의 중대한 결함을 상쇄하지 않는다.

| 최우선 기준 | 확인할 내용 |
| --- | --- |
| 데이터 품질 | 전시명, 시작일, 종료일, 장소, 지역, 유효 상태, 전시 단위 공식 상세 URL, 공식 출처가 각각 확인되는지, 식별자·날짜·상태가 일관적인지, 최신 확인과 정정 근거를 추적할 수 있는지 |
| 확보 가능성 | 이용조건 안에서 반복 접근할 수 있는지, API·파일·공식 페이지가 안정적인지, 식별자나 페이지 구조로 증분 수집할 수 있는지, 호출 제한을 지키며 정해진 재확인 주기와 실패 복구를 운영할 수 있는지 |

두 기준을 통과한 후보 사이에서는 서울·경기·인천의 지역 분포, 기관 유형과 전시 매체·형식의 다양성을 보조 기준으로 사용한다. 유명세나 홍보 규모는 선정 근거가 아니다. 실제 기관명, 출처별 허용 필드와 호출 제약은 [`sources.yaml`](../../sources.yaml)에서 확정한다.

#### 후보 기관 사전 검토

최종 allowlist에 넣기 전 후보 기관마다 공식 출처에 게시된 최근 전시 5건을 수동으로 검토한다. 이 단계는 전체 수집기 구현이나 대량 적재가 아니라, 적은 표본으로 아래 위험을 먼저 찾는 절차다.

- 전시명, 시작일, 종료일, 장소, 지역, 유효 상태, 공식 상세 URL, 공식 출처 중 어느 항목이라도 누락되거나 모순되는지
- 최근 정보가 실제로 갱신되는지와 종료·취소·변경을 확인할 수 있는지
- 전시별 안정된 URL·식별 단서와 반복 접근 가능한 페이지 구조가 있는지
- 이용조건·robots·호출 제한 안에서 후속 수집과 재확인을 운영할 수 있는지

기관별 표본, 항목별 `CORE_PASS` 여부, 확인 시각, 누락·충돌, 접근 제약과 종합 판단을 출처 등록부의 선정 평가 근거로 남긴다.

#### 기관 단위 allowlist 판정과 onboarding lifecycle

1. 기관은 사전 심사를 시작할 때 `CANDIDATE`다. 최근 전시 5건 각각에 아래 전시 단위 최소 품질 게이트를 적용한다.
2. 5건 중 최소 4건이 `CORE_PASS`여야 표본 합격률 조건을 통과한다.
3. 표본 합격률을 통과하더라도 실패 건이 같은 필수 필드의 반복적·구조적 누락을 나타내면 allowlist 등록을 보류한다. 4/5처럼 표본 안의 실패가 한 건뿐인 경우에도 해당 페이지 유형의 출처 템플릿·필드 매핑, 이전 수집 이력 또는 추가 공식 페이지 점검에서 같은 누락이 재현되는지 확인하고 근거를 기록한다. 한 건의 우연한 누락만으로 반복성을 단정하지 않는다.
4. 이용조건·라이선스·robots·호출 제한·인증·CAPTCHA 등 정책 또는 접근 제한이 반복 수집과 재확인을 방해하면 합격률과 관계없이 등록을 보류한다. 접근 통제를 우회해 통과시키지 않는다.
5. 보류된 심사는 `HOLD` 결과와 사유를 남기고 `CANDIDATE`에서 진행하지 않는다. `HOLD`는 lifecycle 상태가 아니다.
6. 심사를 통과한 기관의 첫 allowlist 상태는 `PROVISIONAL`이다. `PROVISIONAL`과 `ACTIVE` 모두 정상 Source에서 수집되고 레코드별 최소 품질·권리·최신성·충돌 게이트를 통과한 데이터는 정본·검색·추천·일반 사용자 서비스에 사용할 수 있다. `ACTIVE`는 유일한 게시 허가 상태가 아니라 실제 변경 처리까지 검증한 고신뢰 상태다.
7. lifecycle은 `CANDIDATE → PROVISIONAL → ACTIVE → SUSPENDED → PROVISIONAL`로 관리한다. `ACTIVE → SUSPENDED`의 반복 실패·Critical 판정은 아래 수집 health 규칙을 따르며, 문제를 수정·승인한 뒤 `PROVISIONAL`로 돌아오면 승격 검증 기간과 연속 성공을 새로 시작한다.

#### `PROVISIONAL → ACTIVE` 승격 기준

다음 조건을 모두 만족한 경우에만 `ACTIVE`로 승격한다.

1. `promotion_validation_started_at + 14일`이 지났다.
2. `InstitutionQualificationRun.finished_at`을 `Asia/Seoul` 달력일로 환산한 날짜가 서로 다른 최종 `SUCCESS` 실행 3회가 연속되며, 첫 성공부터 세 번째 성공 사이에 해당 기관 범위의 최종 `FAILED` 실행이 없다. 같은 날짜의 성공을 여러 번 실행해도 한 날짜로만 센다.
3. 세 성공 실행 중 최소 1회가 실제 신규 또는 의미 있는 변경 전시를 감지하고 `SourceRecord → 정규화 → Canonical Exhibition 반영 → ChangeHistory 기록`을 끝까지 완료했다.
4. 세 실행에서 치명적 수집 실패, 구조적 핵심 필드 누락, 정책·robots·약관 문제, CAPTCHA·로그인 요구와 지속 접근 차단이 각각 0건이다.
5. 승격 시점의 마지막 검증 실행이 `SUCCESS`이고 승격 대상 Source 운영 상태가 정상이며 미해결 구조적 `SourceConflict`가 0건이다.

HTTP 요청이 일시적으로 실패해 재시도했더라도 허용 횟수 안에서 모든 핵심 대상 페이지를 끝까지 처리하고 해당 기관의 최종 상태가 `SUCCESS`이면 성공으로 인정한다. `request_retry_count > 0`만으로 연속 성공을 끊지 않는다. 반대로 `PROVISIONAL` 기관의 InstitutionRunResult가 `FAILED`이거나 핵심 대상 페이지를 끝내 수집하지 못했거나, 핵심 데이터가 미완성인 채 Canonical 데이터에 반영되거나 실행 중 Critical이 확인되면 연결된 InstitutionQualificationRun도 최종 `FAILED`로 기록하고 승격 연속 성공을 초기화한다. 공유 IngestionRun의 전체 상태가 다른 기관 때문에 `FAILED`여도 해당 기관의 InstitutionRunResult가 `SUCCESS`라면 그 기관의 QualificationRun을 실패로 바꾸지 않는다. 선택 필드만 제공하는 대상·selector 실패와 가져온 단일 불합격 레코드의 정상 격리는 이 실패 정의와 구분한다.

승격 성공일은 명시적인 자격 검증 실행만 만든다. P0 구현에서는 `sync_exhibitions --qualification`이 승인 표본 수만큼 핵심 대상을 처리한 경우에만 InstitutionQualificationRun을 기록하며 일반 증분 sync와 단일·due 재확인은 승격 성공일에 포함하지 않는다.

#### `ACTIVE` 수집 health와 `SUSPENDED` 판정

InstitutionAllowlistEntry의 `health`는 lifecycle과 Source 운영 상태에서 독립된 `HEALTHY` 또는 `DEGRADED`다. `PROVISIONAL`과 `ACTIVE` 모두 health를 가지지만 연속 최종 실패 수와 아래 2회 자동 중단 사다리는 `ACTIVE`에만 적용한다. 같은 IngestionRun에서 발생한 여러 요청·재시도는 실행 1회로만 센다. 공유 Source 실행도 InstitutionRunResult를 기관별로 하나씩 만들어 서로 영향을 주지 않는다.

1. 허용 재시도를 소진한 첫 최종 `FAILED`는 `ACTIVE`를 유지하고 `health = DEGRADED`, `consecutive_final_failed_count = 1`로 기록한다. 해당 기관은 출처 호출 제한과 backoff를 지키는 가장 이른 시점의 우선 재검증 대상이다.
2. 중간 최종 `SUCCESS` 없이 서로 다른 IngestionRun ID의 기관별 결과 2개가 연속 `FAILED`이면 `ACTIVE → SUSPENDED`로 전환한다. 같은 실행의 HTTP 재시도는 두 번째 실패로 세지 않는다.
3. 다음 기관별 최종 결과가 `SUCCESS`이면 연속 실패 수를 0으로 초기화한다. 미해결 `STRUCTURAL_OPTIONAL`이 없으면 `HEALTHY`로 복구하고, 남아 있으면 `DEGRADED`를 유지한다.
4. `POLICY_BLOCK`, `ACCESS_BLOCK`, `STRUCTURAL_CRITICAL`은 실패 수와 관계없이 확인 즉시 `ACTIVE → SUSPENDED`로 전환하고 추가 자동 요청을 중단한다. 실행 중 확인됐다면 영향 기관의 InstitutionRunResult와 이를 포함한 IngestionRun을 최종 `FAILED`로 기록하고 `ACTIVE` 실패 수를 기존 0에서 1 또는 1에서 2로 올리되, 중단 자체는 수치를 기다리지 않는다. 실행 밖 정책·구조 검토에서 확인됐다면 CollectionIssue와 상태 전이만 기록하고 가상 IngestionRun·InstitutionRunResult나 실패 수를 만들지 않는다.

| 분류 | 확정 기준 | 처리 |
| --- | --- | --- |
| `POLICY_BLOCK` | 이용약관이 자동 수집을 금지하거나, 수집 허용 여부에 영향을 주는 중대한 변경이 해결되지 않은 채 불명확함; robots 정책이 대상 경로 수집을 금지함 | 즉시 `SUSPENDED`, 자동 수집 중단, 운영 검토 |
| `ACCESS_BLOCK` | CAPTCHA, 로그인 필수화, 한 실행의 허용 재시도 안에서 반복되는 403·bot 차단, 접근 통제 우회 필요 | 즉시 `SUSPENDED`, 우회 금지 |
| `STRUCTURAL_CRITICAL` | 전시명·시작일·종료일·장소·지역·유효 상태·공식 상세 URL·공식 출처 중 하나 이상의 기관·템플릿 수준 안정적 추출 불가, 핵심 오값 대량 생성 위험, 목록과 상세의 신뢰 가능한 연결 상실 | 즉시 `SUSPENDED`, 영향 레코드 반영 금지 |
| `STRUCTURAL_OPTIONAL` | 요금·예약·관람시간·접근성·감각·미디어처럼 최소 품질 밖 필드의 구조·selector만 실패하고 핵심 대상은 정상 처리됨 | 실행 `SUCCESS` 가능, 값 `UNKNOWN` 또는 이미지 대체, 현재 `PROVISIONAL`·`ACTIVE` lifecycle 유지 + `DEGRADED`, `ACTIVE` 실패 수 증가 없음 |
| `RECORD_EXCEPTION` | 페이지를 정상 확보·처리했으나 개별 전시 한 건만 핵심 게이트에 실패하고 기관·템플릿 패턴이 아님 | 해당 레코드만 격리, 기관 lifecycle·health·실패 수 유지 |

`RECORD_EXCEPTION`이 같은 핵심 필드·템플릿에서 반복되거나 기관 범위의 대량 오값 위험을 보이면 `STRUCTURAL_CRITICAL`로 재분류한다. 반대로 선택 필드가 `UNKNOWN`이라는 이유만으로 `FAILED`나 `SUSPENDED`를 만들지 않는다. `health`는 staff 운영 정보이며 사용자에게는 각 필드의 `확인 필요`, 최신성·공식 근거만 표시한다.

이 자동 lifecycle 전이는 `ACTIVE`에 적용한다. `PROVISIONAL`은 Critical이 확인되어도 허용되지 않은 새 lifecycle 전이를 만들지 않고 `health = DEGRADED`로 둔다. 대신 미해결 Critical CollectionIssue를 해당 scope의 수집 전 차단 게이트로 사용해 `ACTIVE` 승격과 추가 수집을 중단한다. 실행 중 확인됐다면 InstitutionRunResult와 InstitutionQualificationRun을 최종 `FAILED`로 기록하고 승격 연속 성공을 초기화하며, 실행 밖 검토에서 확인됐다면 가상 실패 실행 없이 기존 승격 증거를 무효화하고 다음 검증 시작 시각을 새로 잡는다. `PROVISIONAL`의 `consecutive_final_failed_count`는 0으로 유지한다. CollectionIssue는 기관 범위인 `ENTRY`가 기본이고, 정책·접근·구조 문제가 공유 Source 전체에 적용된다는 근거가 있을 때만 `SOURCE`로 넓혀 Source 운영 상태와 연결 기관 전체를 일시 중단한다. 문제 해결 후 수집 게이트를 다시 열더라도 승격 검증 증거는 처음부터 다시 쌓고, 다음 기관별 성공과 미해결 선택 구조 문제 유무로 health를 복구한다.

#### 의미 있는 신규·변경의 판정

원본 HTML이나 응답 해시가 달라졌다는 사실만으로 승격 증거를 만들지 않는다. 승인된 정규화 규칙 버전으로 비교한 의미 필드가 달라지고 실제 Canonical Exhibition과 ChangeHistory까지 반영되어야 한다. P0 승격 증거로 인정하는 유형은 아래 표로 닫고, 목록 밖 변화는 별도 결정과 정규화 규칙 버전 승인이 있기 전까지 인정하지 않는다.

| 판정 | 예시 |
| --- | --- |
| 인정 | 새 전시 생성, 종료일 변경·연장, 요금 변경, 장소 변경, 예약 방식 변경, 전시 취소, 공식 설명에서 P0 승인·버전 고정 정규화 규칙이 실제 Canonical 필드 변경을 만든 경우 |
| 불인정 | 페이지 footer·배너 변경, tracking parameter 변경, HTML whitespace·필드 순서 변경, 수집 시각만 변경, 정규화 결과가 같은 원본 해시 변경 |

인정되지 않은 변화는 SourceRecord와 수집 이력에는 남길 수 있지만 `ACTIVE` 승격을 위한 의미 있는 변경 횟수에는 포함하지 않는다. 전시명·시작일·지역·일반 상태 전이처럼 목록에 없는 변화는 그 자체로 승격 증거가 아니며, 범위를 늘리려면 결정 등록부와 버전 고정 정규화 규칙을 먼저 함께 갱신한다. 취소만 상태 변경 유형의 명시적 예외다.

#### 전시 단위 최소 품질 합격 기준

전시 한 건의 최소 품질 합격에는 다음 항목이 모두 필요하다.

| 핵심 항목 | 확인 기준 |
| --- | --- |
| 전시명 | 공식 출처의 전시 단위 대표 명칭을 확인할 수 있음 |
| 시작일 | 정확한 달력 날짜와 근거를 확인할 수 있음 |
| 종료일 | 정확한 달력 날짜와 근거를 확인할 수 있고 시작일보다 이르지 않음 |
| 장소 | 실제 개최 장소를 확인할 수 있음 |
| 지역 | 개최 장소와 연결된 행정 지역을 확인할 수 있음 |
| 유효 상태 | 공식 기간·취소 근거로 `UPCOMING`, `CURRENT`, `ENDED`, `CANCELED` 중 하나를 신뢰성 있게 판정할 수 있음 |
| 공식 상세 URL | 해당 전시 한 건을 설명하는 공식 상세 페이지로 연결됨 |
| 공식 출처 | 출처 등록부에서 책임 주체와 공식성을 확인하고 필드 증거를 추적할 수 있음 |

모든 핵심 항목을 통과한 표본 전시의 판정값이 `CORE_PASS`다. 하나라도 누락·무효·충돌이면 `CORE_PASS`가 아니며 정상 검색·추천 정본으로 승격하지 않는다. 요금, 예약, 관람시간, 접근성, 감각 정보는 이 합격 기준에 포함하지 않는다. 이 값들이 공식 근거로 확인되지 않으면 `UNKNOWN`으로 남기고 다른 기관·유사 전시·평균값으로 추론하지 않는다. 다만 사용자가 해당 값을 필수 방문 조건으로 지정한 요청에서는 `UNKNOWN`을 충족으로 판단하지 않는다.

### 3.2 1순위 — 공식 구조화 데이터

- 정부·지자체·공공기관이 제공하는 공개 API
- 공식 기관이 배포하는 기계 판독 가능한 데이터 파일
- 기관 또는 주최자가 문서화해 제공하는 공식 피드

구조화 데이터는 안정된 식별자와 반복 수집에 유리하지만, 갱신 지연이 있을 수 있으므로 운영시간·휴관·취소·예약처럼 변동성이 높은 값은 기관의 최신 공지와 함께 확인한다.

### 3.3 2순위 — allowlist에 등록된 공식 웹페이지

- 전시를 운영하는 기관의 전시·이용안내 페이지
- 주최·주관 기관이 직접 관리하는 행사 페이지
- 작품을 소장한 기관의 공식 소장품 페이지

접근이 공개되어 있고 이용조건과 로봇 정책이 수집을 허용하는 경우에만 사용한다. 페이지 구조를 우회하거나 과도한 요청으로 서비스에 부담을 주어서는 안 된다.

### 3.4 3순위 — 공식 보도자료와 공지

구조화 데이터나 상시 페이지에서 얻을 수 없는 취소·기간 변경·임시 휴관 등의 보완 근거로 사용한다. 보도자료가 오래된 상시 페이지와 충돌하면 발행 시각과 책임 주체를 함께 검토한다.

## 4. P0 데이터 범위

P0는 현재·예정 전시와 `2023-01-01` 이후 전시의 품질 검증을 우선한다. 이 기준은 오래된 공식 전시를 삭제하거나 검색에서 일괄 제외하는 컷오프가 아니다. 더 오래된 공식 데이터도 안정적으로 확보되고 출처·권리·관계가 검증되면 종료 전시 아카이브로 보존할 수 있다.

지역 구조는 대한민국 전역을 수용하되 초기 품질 검증은 서울·경기·인천을 우선한다. 지역이나 시기별 데이터가 적다는 사실을 커버리지 완성으로 과장하지 않는다.

## 5. 정식 사실 근거로 사용하지 않는 출처

- 개인 블로그, 커뮤니티, 리뷰, 언론 기사와 제3자 요약
- SNS 게시물만 존재하고 별도 공식 개최 근거를 확인할 수 없는 행사
- 티켓 판매처·플랫폼이 제공하는 값을 공식 기관 확인 없이 정본으로 삼는 방식
- 검색 결과 스니펫, 지도 서비스의 사용자 편집 정보
- 로그인, CAPTCHA, 유료벽 또는 접근 통제를 우회해야 하는 페이지
- 이용조건이나 자동 접근 허용 여부를 확인할 수 없는 출처
- 출처·라이선스·권리자를 추적할 수 없는 복제 데이터와 미디어

이 자료들은 운영자가 공식 출처를 찾는 단서가 될 수는 있지만, 그 자체로 사용자에게 표시할 정식 사실이나 추천 근거가 되지 않는다.

## 6. 후보 심사 기록과 출처 등록부

수집 전 각 기관 후보는 심사 기록을 가져야 하고, 심사를 통과해 등록하는 각 Source는 출처 등록부에 승인되어야 한다. 두 기록은 최소한 다음 판단 근거를 보존한다.

| 항목 | 정책상 의미 |
| --- | --- |
| 출처 소유·책임 주체 | 어떤 사실에 대해 공식성을 갖는지 |
| 접근 위치와 방식 | API, 데이터 파일, 공식 페이지 등 |
| 허용 데이터 범위 | 전시, 작품, 기관, 방문정보, 미디어 중 수집 가능한 범위 |
| 이용조건·라이선스 | 저장·가공·표시·재배포가 허용되는 범위 |
| 로봇·호출 제한 | 자동 접근 가능 여부와 지켜야 할 제한 |
| 권리 검토 기록 | 검토 일자, 근거 문서, 재검토가 필요한 조건 |
| 필드별 권위 | 해당 출처가 정본으로 책임지는 값 |
| 기관 후보 심사 | 최근 5건의 항목별 `CORE_PASS`, 합격 건수, 추가 구조 증거를 포함한 반복 누락, 정책·접근 제한, 평가 시각과 `PASS`·`HOLD` 결과 및 사유 |
| 기관 allowlist 상태 | `CANDIDATE`, `PROVISIONAL`, `ACTIVE`, `SUSPENDED`, 상태 변경 시각·사유·승인 근거와 `HOLD` 심사 결과 |
| 기관 수집 health | `HEALTHY`, `DEGRADED`, 변경 시각·사유, 연속 최종 실패 수, 우선 재검증 시각·근거와 미해결 선택 구조 문제 |
| 승격 검증 근거 | 최초 검증 시작 시각, 서로 다른 날짜의 연속 성공 실행, 중간 실패 여부, 재시도와 최종 상태, 의미 있는 변경의 SourceRecord·정규화·Canonical·ChangeHistory 연결, Source 운영 상태와 미해결 구조 충돌 수 |
| Source 운영 상태 | 정상, 일시 중단, 사용 중지와 그 사유 |
| 수집 문제 분류 | `POLICY_BLOCK`, `ACCESS_BLOCK`, `STRUCTURAL_CRITICAL`, `STRUCTURAL_OPTIONAL`, `RECORD_EXCEPTION`, `ENTRY`·`SOURCE` scope와 범위 확대 근거, 영향 Source·기관·필드·레코드, 확인·해결 근거 |

`HOLD` 심사는 사유와 증거를 보존하지만 서비스 allowlist 등록으로 취급하지 않는다. 등록부에 없거나 운영 상태가 사용 중지인 Source는 신규 수집에 사용하지 않는다. 일반 동기화에는 `PROVISIONAL` 또는 `ACTIVE`인 기관 항목, 정상 Source, 영향 scope의 미해결 Critical CollectionIssue 0건을 모두 요구한다. 사용자 데이터 게시에는 레코드별 품질·권리·최신성·충돌 게이트를 별도로 적용한다. `CANDIDATE`와 `SUSPENDED`는 신규 수집·정본 반영·파생본 생성 대상이 아니다. 하나의 Source가 여러 기관에 공유되면 기관별 lifecycle과 CollectionIssue scope를 따로 적용한다. 실제 기관은 승인된 [`sources.yaml`](../../sources.yaml) 밖에서 임의로 추가하지 않는다.

## 7. 필드별 출처 우선순위와 충돌

하나의 출처가 모든 필드의 정본일 필요는 없다.

| 데이터 종류 | 우선 근거 |
| --- | --- |
| 전시 취소·기간 변경·임시 휴관·예약 | 해당 전시 운영 기관 또는 주최자의 최신 공식 공지 |
| 전시명·기간·장소 | 주최·운영 기관의 공식 전시 페이지, 그다음 공식 구조화 데이터 |
| 기관 운영시간·휴관·접근성 | 해당 기관이 직접 관리하는 최신 이용안내 |
| 작품명·작가·제작연도·소장관계 | 소장 기관의 공식 소장품 데이터 |
| 표준 식별자·행정구역 코드·주소·좌표 | 승인된 공식 API·공공 구조화 데이터 |

충돌 시 최신 시각만으로 자동 결정하지 않는다. 사실 책임 주체, 변경 공지의 명시성, 원본 확인 시각을 함께 보고 채택한다. 자동 판정이 불가능하면 충돌 상태를 남기고 현재 추천에서 제한하며 운영 검토 대상으로 보낸다.

## 8. 텍스트와 구조화 요약

- 공식 제목, 짧은 사실 문구와 구조화 값은 출처·라이선스 범위에서 보존한다.
- 긴 소개문 전체를 필요 이상으로 복제하지 않는다. 표시 목적에 필요한 범위와 허용 조건을 확인한다.
- 서비스가 만든 요약은 공식 설명과 구분하고, 공식 메타데이터와 명시적 소개 문구 안에서 구조화한다.
- 작가의 의도, 작품 의미, 관객 반응처럼 근거에 없는 해석을 생성하지 않는다.
- 삭제·정정 요청 또는 권리 변경이 확인되면 원문 표시를 중단할 수 있어야 하며, 사실 이력과 운영 감사 기록은 별도 보존 원칙을 따른다.

## 9. 미디어 권리 정책

메타데이터의 사용 가능 여부와 이미지·음원·영상의 사용 가능 여부를 분리해 판정한다.

| 권리 판정 | 허용되는 처리 |
| --- | --- |
| 재사용 허용 확인 | 확인된 라이선스·이용조건과 표시 의무 안에서 저장·변환·표시 가능 |
| 원본 링크만 허용 | 미감이 복제하지 않고 공식 원본 페이지로 연결 |
| 권리 미확인 | 서비스 표시·취향 테스트·데모 번들에서 제외 |
| 사용 불가 또는 철회 | 신규 사용과 사용자 표시를 중단하고 파생본도 제거 대상에 포함 |

추가 규칙은 다음과 같다.

1. 포스터·공간 사진·작품 이미지·인물 사진·영상 썸네일을 서로 별도의 미디어로 보고, 권리자, 라이선스, 출처, 필수 크레딧, 허용 범위와 확인 시각을 각각 기록한다.
2. 원본 URL이 공개되어 있다는 이유만으로 다운로드·캐시·썸네일 생성·핫링크가 허용된다고 보지 않는다.
3. 취향 테스트에는 서비스 내 재사용이 확인된 실제 이미지 또는 미디어 없는 경험 시나리오만 사용한다.
4. 실제 음원과 전체 영상은 P0 취향 테스트에 임의로 재호스팅하거나 재생하지 않는다.
5. 권리가 바뀌거나 확인되지 않으면 타이포그래피 기반 대체 표현으로 기능을 유지한다.
6. 이미지가 없다는 이유만으로 권리와 메타데이터가 검증된 전시를 검색·추천에서 제외하지 않는다.

## 10. 데모 데이터와 재배포

P0 데모는 외부 키와 실시간 수집 없이 반복 실행할 수 있어야 한다. 다만 저장소에 포함되는 데모 레코드와 미디어는 다음을 만족해야 한다.

- 레코드마다 공식 출처와 확인 시각을 추적할 수 있음
- 사실값의 복제·가공 범위가 이용조건에 부합함
- 미디어는 재배포 가능한 권리가 명시적으로 확인되거나 번들에서 제외됨
- 데모용으로 축약·가명화한 값은 실제 공식 값과 혼동되지 않게 구분됨
- 공개 저장소·프로젝트 라이선스·데모 재배포 범위는 OD-002 결정 전에는 외부 배포를 전제하지 않음

## 11. 위반·변경 대응

정책·접근·구조 변화는 위 분류표로 먼저 범위와 심각도를 판정한다. `POLICY_BLOCK`·`ACCESS_BLOCK`·`STRUCTURAL_CRITICAL`만 `ACTIVE`를 즉시 `SUSPENDED`로 전환하고 신규 수집을 중지하며, `PROVISIONAL`은 미해결 Critical CollectionIssue로 해당 범위를 차단한다. `STRUCTURAL_OPTIONAL`은 선택값을 `UNKNOWN`으로 낮추고 health를 `DEGRADED`로 두며, `RECORD_EXCEPTION`은 해당 레코드만 격리한다. 이미 검증된 사실을 실패 응답이나 빈 값으로 덮어쓰지 않는다. `SUSPENDED`나 Critical이라는 이유만으로 마지막 정상 정본을 일괄 제외하지 않고 최신성·권리·충돌로 다시 판정하되, Critical 근거가 현재 핵심값 자체의 신뢰를 훼손하는 영향 레코드는 즉시 `EXCLUDED`로 격리한다. 문제 수정과 정책 재승인 후에는 `PROVISIONAL`에서 승격 검증을 처음부터 다시 수행한다. 조치 이력은 원본 데이터와 분리해 감사 가능하게 남긴다.
