# 미감 P0 테스트 계획

## 1. 목적과 현재 상태

이 문서는 P0를 데이터 입력부터 사용자 판단까지 반복 검증하는 방법을 정의한다. 현재 저장소에는 구현 코드와 실행 매니페스트가 없으므로 존재하지 않는 명령을 만들지 않는다. 구현 후에는 실제 `package.json`, `pyproject.toml`, 컨테이너 구성과 자동화 설정에서 확인한 명령만 이 문서의 다음 버전에 기록한다.

검증 기술의 방향은 다음과 같이 확정되어 있다.

- 데이터 파이프라인·Django 서비스·DRF API의 단위·통합 테스트
- Vitest와 React Testing Library 기반 프론트 단위·컴포넌트 테스트
- OpenAPI 계약과 프론트 경계 검증
- Playwright 기반 사용자 E2E
- Chromium 전체 E2E, Firefox·WebKit 핵심 스모크
- 자동 접근성 검사와 키보드·스크린리더·확대·모션 감소 수동 검증

## 2. 테스트 원칙

1. **불변식을 먼저 검증한다.** 하드 필터, 전시 상태, 추천 이유, 이미지 권리 위반은 평균 점수로 상쇄할 수 없다.
2. **외부 서비스 없이 재현한다.** 핵심 검증은 고정 픽스처와 대표 데모 데이터로 실행하고 외부 API·지도 실패도 주입한다.
3. **경계에서 계약을 검증한다.** 원본 데이터→정규화, 서비스→API, API→프론트 어댑터, 브라우저 저장소 버전 경계를 각각 검사한다.
4. **성공·빈·오류·저하 상태를 함께 다룬다.** 정상 경로만 통과해도 완료로 보지 않는다.
5. **사용자 행동을 취향 신호와 분리한다.** 조회·검색·비교·지도·최근 본 전시가 추천을 바꾸지 않는지 회귀 검증한다.
6. **테스트가 데이터 권리를 약화하지 않는다.** 테스트 이미지도 재사용 허용 자산 또는 저장소에서 만든 명시적 테스트 자산만 사용한다.

## 3. 테스트 데이터

### 3.1 결정적 소형 픽스처

단위·통합 테스트는 각 규칙의 경계값을 분리한 작은 고정 데이터를 사용한다.

- 전시 상태: 현재, 예정, 종료, 공식 취소, 충돌 후보
- 최신성: `FRESH`, `STALE`, `UNVERIFIED`, 수집 실패
- 날짜: 시작·종료 경계, 하루 겹침, 일부 겹침, 공식 휴관일
- 지역: 시·도 전체, 시·군·구, 좌표 있음·없음
- 요금: 무료, 성인 기본권, 여러 연령 가격, 할인·얼리버드·패키지, 미확인
- 예약·관람시간: 공식, 근거 있는 추정, 미확인
- 접근성·감각: 충족, 충돌, 미확인
- 이미지: `REUSE_ALLOWED`, `LINK_ONLY`, `RIGHTS_UNKNOWN`, 없음, 로딩 실패
- 출처: 필드별 우선순위, 동일 값, 충돌, 공식 페이지 삭제
- 중복: 강한 자동 병합, 모호한 후보, 순회전
- 추천: 취향 없음, 테스트만, 관심 1~2개, 충분한 명시 신호, 종료·미확인 후보 혼입

### 3.2 대표 E2E 데이터

E2E 데이터는 서울·경기·인천을 중심으로 일부 비수도권을 포함하고, 전시·작품·기관·상태·매체·가격·권리·접근성 예외를 모두 재현해야 한다. 데이터 크기가 확대되어도 같은 시나리오 식별자는 유지한다.

### 3.3 데모 데이터 규모 목표

P0 대표 데모 데이터는 전시 300~500, 작품 500~1,000, 기관 약 100을 목표로 한다. 이 수치는 화면 성능과 탐색 품질을 검증하기 위한 목표이며 테스트 성공을 위해 외부 출처에서 권리 불명확 자료를 채워 넣는 근거가 아니다.

## 5. 실행 환경

### 5.1 기본 모드

- 단위·통합·컴포넌트·E2E는 외부 네트워크 호출을 기본 차단하고 고정 픽스처를 사용한다.
- 시간·현재 날짜·위치·지도 응답을 제어할 수 있어야 한다.
- 각 테스트는 브라우저 저장값, 데이터베이스, 캐시와 비교 선택을 독립적으로 초기화한다.
- 무작위 다양성 재정렬은 시드 또는 고정 결과로 재현 가능해야 한다.

### 5.2 통합 재현 모드

네이티브 개발 환경과 컨테이너 통합 환경에서 동일한 핵심 픽스처 결과가 나와야 한다. 컨테이너 검증은 외부 API 키 없이 프론트·백엔드·데모 데이터가 함께 동작하는지 확인한다.

### 5.3 외부 출처 계약 확인

실제 공공 API와 기관 수집기 검증은 승인된 출처별로 별도 수행한다. 이 검증은 호출 제한과 이용조건을 지키고, 실패가 핵심 오프라인 테스트 결과를 불안정하게 만들지 않도록 자동 게이트와 분리한다.

## 6. 브라우저 검증 범위

### 전체 자동화

Chromium에서 `TEST-016`~`TEST-027` 전체, 접근성 자동 검사, 데스크톱·모바일 반응형 핵심 상태를 수행한다.

### 스모크 자동화

Firefox와 WebKit에서는 다음을 최소 수행한다.

- 홈 두 경로 진입
- 전시 검색·필터·상세
- 전시 관심과 새로고침 후 브라우저 저장 유지
- 취향 테스트 핵심 흐름
- 종료·권리 없는 이미지 상태

### 실제 환경 확인

최신 Edge·Safari, Android Chrome·iOS Safari에서는 터치, 바텀시트, 하단 내비게이션, 확대, 위치 거절과 목록 복귀를 포함한 핵심 과업을 확인한다.

## 7. 접근성 검증 방식

자동 검사만으로 합격시키지 않는다.

1. 핵심 화면의 자동 접근성 검사
2. 키보드만으로 `TEST-016`~`TEST-025`의 대표 행동 수행
3. 대화상자·바텀시트·팝오버·드롭다운의 포커스 수동 확인
4. 스크린리더로 상태·관심·필터·오류·비교 구조 확인
5. 브라우저 확대에서 홈, 탐색, 상세, 비교, 데이터 삭제 수행
6. 모션 감소 설정에서 비필수 효과 제거 확인
7. 이미지 비표시 상태에서 대체 텍스트와 텍스트형 카드 정보 동등성 확인

자동 도구의 오탐을 제외할 때는 검사 위치, 이유, 수동 확인 결과를 증거에 남긴다. 핵심 과업을 막는 미해결 접근성 문제는 합격으로 처리하지 않는다.

## 8. 품질 게이트

### 변경 단위 게이트

- 변경한 계층의 단위·계약·컴포넌트 테스트 통과
- 연결된 `AC-###`와 추적성 매트릭스 동기화
- 무관용 불변식 위반 없음
- 권리·개인정보·접근성 회귀 없음

### P0 후보 게이트

- `TEST-001`~`TEST-037` 중 구현 범위에 해당하는 필수 시나리오 통과
- `TEST-016`~`TEST-027` Chromium 전체 통과
- Firefox·WebKit 스모크 통과
- 최신 주요 브라우저 핵심 과업 확인
- 접근성 자동·수동 검증 완료
- 외부 출처가 없어도 대표 데모 데이터로 재현
- 실패 테스트를 재시도만으로 숨기지 않으며 불안정 테스트가 남아 있지 않음

## 10. 검증 증거

각 테스트 실행은 다음을 남긴다.

- 실행 시각과 코드·문서 버전
- 테스트 데이터 또는 픽스처 버전
- 실행 환경, 브라우저·OS 버전
- 통과·실패·제외 수와 실패 원인
- E2E 실패 시 스크린샷·트레이스 등 재현 자료
- 접근성 수동 검토자, 보조기술·설정과 결과
- 외부 출처 계약 확인 시 출처와 확인 시점

명령 이름을 증거보다 먼저 문서에 고정하지 않는다. 구현된 공식 실행 경로가 생기면 검증 결과와 함께 이 문서를 갱신한다.
