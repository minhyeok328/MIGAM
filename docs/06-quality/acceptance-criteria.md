# 미감 P0 합격 기준

## 1. 판정 원칙

P0는 기능이 화면에 존재하는지만으로 합격하지 않는다. 대표 데이터에서 `발견 → 이해 → 판단` 흐름을 완수하고, 데이터·추천·권리·접근성 불변식을 함께 만족해야 한다.

- 각 `AC-###`의 조건을 모두 충족해야 해당 항목이 통과한다.
- 자동 검증과 수동 검증이 함께 지정된 항목은 둘 다 통과해야 한다.
- 외부 출처나 지도 제공자의 실패는 정상적인 저하 시나리오로 검증한다.
- 현재 Django 구현은 `uv run --project backend python backend/manage.py test tests --verbosity 1`, TP-006 프론트는 `frontend`의 `npm test`, `npm run api:check`, `npm run build`로 검증한다. 아직 구현되지 않은 E2E는 각 승인 작업 패킷에서 실제 러너를 추가한다.

TP-006은 `AC-001`의 계정 없는 홈과 탐색 진입 일부, `AC-004`~`AC-008` 중 검색·방문 조건 입력·필수/선호 구분·별도 확인 후보·실제 이유 카드, `AC-014`·`AC-015`·`AC-018`·`AC-020` 중 비영속 입력·안전한 미디어·오류 회복·Radix 포커스·reduced-motion의 첫 프론트 범위를 검증한다. 생성 계약은 `frontend/src/test/contract.typecheck.ts`, 요청은 `frontend/src/features/discovery/forms.test.ts`, 응답은 `frontend/src/shared/api/client.test.ts`, 화면 상호작용은 `frontend/src/app/App.test.tsx`, 프록시 로그는 `frontend/src/test/dev-log.test.ts`, 실제 API 데모는 `tests/discovery/test_demo_api.py`에 연결한다. `/`는 API를 호출하지 않고 `/discover`만 입력과 API를 소유한다. TP-006의 입력 비영속 계약에 따라 원문 조건은 URL에 복제하지 않으며 `/discover#recommend`의 고정 탭 식별자를 제외한 새로고침 복원은 구현하지 않는다. 실제 취향 테스트·홈 추천 6개·위치·휴관일·상세와 실제 스크린리더 검수는 제외되어 위 AC 전체 통과를 의미하지 않는다.
- 아래 요구사항 ID는 `prd-p0.md`의 실제 `P0-FR-*`, `P0-NFR-*`, `P0-OUT-*`를 사용한다.

## 2. 무관용 불변식

다음 위반은 허용 건수가 0건이다. 하나라도 재현되면 관련 기능과 P0 전체 판정을 통과시킬 수 없다.

| 불변식 | 근거 요구사항 |

| 추천 이유가 실제 취향 신호·전시 특성과 불일치 | `P0-FR-050`, `P0-FR-052` |

| `CANDIDATE`·`SUSPENDED` 범위의 신규 데이터를 정본·검색·추천에 반영하거나 `PROVISIONAL` 합격 레코드를 상태만으로 배제 | `P0-FR-091` |
| 첫 최종 실패만으로 `ACTIVE`를 중단하거나, 중간 성공 없는 서로 다른 실행 2회 연속 최종 실패·Critical 사유를 중단하지 않거나, 선택 구조 문제·단건 예외만으로 기관을 중단 | `P0-FR-092` |
| 조회·검색·비교·최근 본 기록을 취향 신호로 반영 | `P0-FR-004`, `P0-FR-071`, `P0-OUT-002` |

## 3. 발견 단계

### `AC-001` 계정 없는 두 진입 경로

**추적 요구사항:** `P0-FR-001`, `P0-FR-006`

- 새 브라우저 상태의 사용자가 계정 생성·로그인·서버 익명 프로필 없이 홈을 사용할 수 있다.
- `내 취향부터 알아보기`와 `지금 갈 전시 찾기`가 같은 화면에서 같은 위계의 주요 행동으로 제공된다.
- 어느 경로를 선택해도 현재·예정 전시 후보까지 도달할 수 있다.
- 한 경로를 완료하지 않아도 다른 경로와 통합검색을 사용할 수 있다.

`TP-006`은 이 기준 중 로그인 없는 브랜드 홈, 검색 진입과 조건 추천 진입만 구현한다. 홈의 두 실제 링크는 `/discover`와 `/discover#recommend`로 이동하며 실제 취향 테스트와 현재·예정 후보까지의 전체 흐름은 후속 범위다.

### `AC-002` 적응형 취향 테스트

**추적 요구사항:** `P0-FR-012`~`P0-FR-017`

- 기본 단계는 약 8문항으로 시작하며 추가 문항은 응답에 필요한 축에서만 나오고 최대 4~6문항 범위를 넘지 않는다.
- 복수 카드 선택, 상황 비교, 매체 복수 선택을 대표 시나리오에서 각각 수행할 수 있다.
- `둘 다 좋아요`, `잘 모르겠어요`, `건너뛰기`, 기본 단계 이후 `결과 보기`가 동작한다.
- 미선택·유보·건너뛰기 값은 부정 신호를 만들지 않는다.
- 시각 문항은 재사용 권리 확인 이미지만 사용하고 이미지가 없는 자료는 시각 선택 문항에서 제외한다.
- 음원·전체 영상을 다운로드·재호스팅·자동 재생하지 않아도 테스트를 완료할 수 있다.

### `AC-003` 취향 결과와 재테스트

**추적 요구사항:** `P0-FR-018`~`P0-FR-021`

- 결과는 퍼센트가 아닌 정성적 요약으로 표시되고 각 요약에서 테스트 또는 관심 근거를 확인할 수 있다.
- 탐색이 적은 축을 비선호로 표시하지 않는다.
- 지역·날짜가 없으면 현재·예정 전시 후보를 보여주되 방문 조건을 반영한 추천이 아님을 명시한다.
- 재테스트 후 최신 테스트 결과가 이전 결과를 대체하고, 사용자가 유지한 관심 신호는 남는다.

### `AC-004` 지금 갈 전시 입력

**추적 요구사항:** `P0-FR-022`~`P0-FR-031`

- 지역과 하루 또는 직접 지정 기간을 필수로 받아 조건 검색을 시작한다.
- 지역은 시·도 및 시·군·구 수동 선택으로 완결되며 현재 위치 버튼을 누르기 전에는 위치 권한을 요청하지 않는다.
- 위치 거절·실패 후 수동 지역 선택으로 동일 과업을 완료한다.
- 선택 기간 안에 확인된 휴관·취소가 아닌 관람 가능일이 하루 이상 있어야 후보가 되며, 일부만 가능하면 실제 구간과 휴관일을 구분한다.
- 최대 예산은 일반 성인 1인 기본 관람권을 사용하며 임의 최저가·할인가로 통과시키지 않는다.
- 동행·분위기·매체·공간 유형·행사 형식·예상 관람시간·예약은 선택적으로 입력할 수 있고 미선택을 비선호로 해석하지 않는다. 예약과 예상 관람시간은 `선호` 또는 `필수` 모드를 명시할 수 있으며, 분위기는 최대 3개를 짧은 의미 설명과 함께 선택한다.
- 공식 근거가 부족한 행사 형식은 제목이나 설명의 인상만으로 추정하지 않고 `형식 미확인`으로 남긴다.

### `AC-005` 필수 조건과 미확인 정보

**추적 요구사항:** `P0-FR-032`~`P0-FR-037`

- 알려진 위반값을 가진 전시는 지역·날짜·최대 예산·필수 접근성·회피 감각 조건과 필수로 지정한 예약·예상 관람시간의 일반 추천에서 제외된다.
- 사용자가 필수 방문 조건으로 지정한 요금·예약·예상 관람시간·접근성·감각 정보가 `UNKNOWN`이면 조건 충족으로 간주하지 않는다.
- 요금·예약·예상 관람시간의 `UNKNOWN`은 `추가 확인 필요`로 구분할 수 있지만, 해당 값이 필수인 요청에서는 정상 충족 후보와 섞지 않는다.
- 매체·분위기·공간 유형·행사 형식 같은 선호 정보 미확인은 가점·감점 없이 중립으로 처리한다.
- UI와 추천 요청을 반복해도 시스템이 하드 필터를 자동 변경하지 않는다.

### `AC-006` 0건 결과의 사용자 주도 회복

**추적 요구사항:** `P0-FR-046`, `P0-FR-034`

- 0건 화면에서 현재 검색어와 조건을 확인할 수 있다.
- 분위기·매체 등 선호 조건의 조정안을 제안할 수 있으나 적용은 사용자가 선택한 뒤에만 일어난다.
- 예산 해제는 사용자가 직접 선택한 경우에만 적용된다.
- 지역·날짜·필수 접근성·회피 감각 조건은 자동 완화와 완화 제안 모두에서 유지된다.
- 필수로 지정한 예약·예상 관람시간은 시스템이 자동 완화하지 않는다.
- 조정 후 변경된 조건이 필터 칩과 URL에 즉시 반영된다.

### `AC-007` 탐색·통합검색·추가 로딩

**추적 요구사항:** `P0-FR-038`~`P0-FR-045`

- 통합 검색에서 전체, 전시, 작품·소장품, 기관 탭을 전환하고 각 유형 상세로 이동한다.
- 검색어 없는 전시 탐색은 현재·예정이 기본이며 종료는 상태를 직접 선택해야 나타난다.
- 키워드 검색은 종료 전시도 찾되 현재·예정·종료 상태를 명확히 구분하고 관련도를 개인화보다 우선한다.
- 독립 작가 탭 없이 작가명으로 전시·작품을 찾을 수 있다.
- 최초 24개, 더 보기마다 다음 24개, 총 결과 수가 일치하고 중복 항목이 없다.
- 필터 변경 시 누적 목록이 초기화되고 검색어·필터·정렬은 URL과 새로고침에서 복원된다.
- 예약·예상 관람시간의 `선호`·`필수` 모드를 바꾸면 필터 칩과 URL에 반영되고 새로고침 후 같은 모드로 복원된다.
- 상세에서 뒤로 이동하면 가능한 범위에서 이미 불러온 목록과 위치가 복원된다.
- 검색어 없는 기본 순서는 현재 관람 가능, 사용자 조건·취향 적합, 종료 임박, 예정 시작 임박, 데이터 품질·정보 완성도를 앞선 기준을 깨지 않는 순서로 적용한다.
- 관련도순·추천순·최신 시작일순·종료 임박순·예정 시작일순을 선택할 수 있고, 현재 상태 필터에 의미 없는 정렬은 비활성화하거나 의미가 보존되는 정렬로 전환한 사실을 알린다.

## 4. 이해 단계

### `AC-008` 설명 가능한 추천과 다양성

**추적 요구사항:** `P0-FR-007`~`P0-FR-011`, `P0-FR-047`~`P0-FR-052`

- 취향 신호가 없는 사용자는 현재·예정, 최신성, 정보 품질, 기관·매체 다양성에 기반한 후보를 받는다.
- 적은 신호는 약하게, 최신 테스트와 관심 신호가 쌓인 경우 더 강하게 반영되며 하나의 관심만으로 추천이 한 유형에 고정되지 않는다.
- 홈 대표 추천은 기본 6개이며 고정 데이터 시나리오에서 같은 기관·매체의 과도한 반복을 방지한다.
- 후보가 충분한 시나리오에서는 약 6개 중 1개가 기존 취향과 최소 한 축이 연결된 탐색형 이유를 가진다.
- 사용자 화면에 내부 점수 퍼센트를 노출하지 않는다.
- 카드는 가장 강한 실제 이유 1개, 상세는 존재하는 실제 이유를 최대 3개까지만 보여준다.

## 12. 기관 allowlist lifecycle과 승격

### `AC-026` 상태 전이·서비스 적격성·`ACTIVE` 승격 증거

**추적 요구사항:** `P0-FR-091`, `P0-FR-086`, `P0-FR-088`

- lifecycle은 `CANDIDATE → PROVISIONAL → ACTIVE → SUSPENDED → PROVISIONAL`만 허용하고 전이 시각·사유·검토자·근거를 역추적할 수 있다.
- 정상 Source에 연결된 `PROVISIONAL`과 `ACTIVE` 레코드는 같은 최소 품질·권리·최신성·충돌 게이트를 통과하면 정본·SearchDocument·ContentFeatureSnapshot과 사용자 검색·추천에 사용할 수 있다. `ACTIVE`는 레코드 게이트를 우회하지 않고 `PROVISIONAL`은 상태만으로 합격 레코드를 배제하지 않는다.
- `CANDIDATE`와 `SUSPENDED` 범위에서는 신규 운영 수집·정본 반영·파생본 생성을 하지 않는다. `SUSPENDED` 전환만으로 마지막 정상 정본을 삭제하지 않고 최신성·권리·충돌 기준으로 기존 노출을 재평가한다.
- `promotion_validation_started_at + 14일`이 지나고, `InstitutionQualificationRun.finished_at`을 `Asia/Seoul` 달력일로 환산한 날짜가 서로 다른 최종 `SUCCESS` 3건이 연속되며 첫 성공부터 세 번째 성공 사이에 해당 기관 범위의 최종 `FAILED`가 0건이어야 한다. 같은 날짜의 여러 성공은 한 날짜로만 센다.
- 요청이 일시 실패해도 허용 재시도로 모든 핵심 대상 페이지를 처리하고 해당 기관의 InstitutionRunResult가 최종 `SUCCESS`이면 성공이다. 핵심 대상 페이지가 최종 미수집되거나 해당 결과가 `FAILED`이거나 핵심 데이터가 미완성인 채 Canonical에 반영되거나 실행 중 Critical이 확인되면 `PROVISIONAL` 기관의 InstitutionQualificationRun도 최종 `FAILED`이며 승격 연속 성공을 초기화한다. 공유 IngestionRun 전체가 다른 기관 때문에 `FAILED`여도 해당 기관 결과가 `SUCCESS`이면 그 QualificationRun은 실패가 아니다. 선택 대상 실패와 정상 격리된 단건 예외는 이 실패 정의에 포함하지 않는다.
- 세 성공 중 최소 1회가 의미 있는 신규·변경을 `SourceRecord → 승인 정규화 규칙 → Canonical Exhibition 생성·갱신 → ChangeHistory`까지 완료해야 한다. P0 인정 유형은 새 전시, 종료일 변경·연장, 요금 변경, 장소 변경, 예약 방식 변경, 전시 취소, 공식 설명에서 P0 승인·버전 고정 정규화 규칙이 만든 Canonical 필드 변경으로 제한한다. 전시명·시작일·지역·일반 상태 전이를 포함한 목록 밖 변화는 별도 결정과 규칙 버전 승인 전까지 인정하지 않으며 취소만 상태 변경 유형의 예외다.
- footer·배너, tracking parameter, HTML whitespace·필드 순서, 수집 시각·재시도 횟수와 정규화 결과가 같은 raw hash 변경은 의미 있는 변경으로 세지 않는다.
- 세 실행의 치명적 수집 실패·구조적 핵심 필드 누락·정책·robots·약관 문제·CAPTCHA·로그인 요구·지속 접근 차단이 각각 0건이어야 한다. 승격 순간에는 마지막 실행 `SUCCESS`, Source 정상, 미해결 구조적 `SourceConflict` 0건을 다시 확인한다.
- `ACTIVE` 운영 health와 `SUSPENDED` 판정은 `AC-027`을 따른다. 중단 사유를 수정·승인한 뒤 `PROVISIONAL`로 돌아가면 14일·연속 성공·의미 변경 검증을 처음부터 다시 수행한다.

## 13. 기관 수집 health와 운영 중단

### `AC-027` 최종 실패·Critical·선택 구조·단건 격리

**추적 요구사항:** `P0-FR-091`, `P0-FR-092`, `P0-FR-086`, `P0-FR-088`, `P0-FR-089`

- InstitutionAllowlistEntry의 `HEALTHY`·`DEGRADED` health는 lifecycle, Source의 정상·일시 중단·사용 중지 운영 상태, 레코드 DataEligibility와 서로 다른 축이다. `PROVISIONAL`과 `ACTIVE` 모두 health를 가지지만 연속 최종 실패 수와 2회 자동 중단 사다리는 `ACTIVE`에만 적용한다. `DEGRADED`·`SUSPENDED`만으로 마지막 정상 정본을 일괄 제외하거나 Source를 중단하지 않으며, 핵심값 자체가 신뢰 불가하다는 Critical 근거가 있는 영향 레코드만 `EXCLUDED`로 격리한다.
- `ACTIVE` 기관의 연속 최종 실패는 서로 다른 IngestionRun ID에 속한 InstitutionRunResult만 센다. 같은 실행 안의 HTTP 실패·재시도는 여러 번이어도 한 실행이며, 재시도로 모든 핵심 대상을 처리한 최종 `SUCCESS`는 실패가 아니다.
- 첫 최종 `FAILED`는 lifecycle `ACTIVE`를 유지하고 `health = DEGRADED`, `consecutive_final_failed_count = 1`로 기록하며 출처 호출 제한·backoff 안에서 가장 이른 우선 재검증 대상으로 올린다. 다음 기관별 최종 결과가 `SUCCESS`이면 실패 수를 0으로 초기화하고 미해결 `STRUCTURAL_OPTIONAL`이 없을 때 `HEALTHY`로 복구한다.
- 중간 최종 `SUCCESS` 없이 서로 다른 IngestionRun의 두 번째 기관별 최종 `FAILED`가 이어지면 `ACTIVE → SUSPENDED`로 전환한다. 두 실행은 서로 다른 날짜일 필요가 없으며 승격용 3개 성공 날짜와 별도 판정이다.
- `POLICY_BLOCK`은 자동 수집 불허·수집 허용에 영향을 주는 중대한 약관 변경의 미해결 불명확성·robots 대상 경로 금지, `ACCESS_BLOCK`은 CAPTCHA·로그인 필수·한 실행 안의 반복 403/bot 차단·우회 필요다. 확인 즉시 추가 자동 요청을 중단하고 실패 수와 관계없이 `ACTIVE → SUSPENDED`로 전환한다.
- `STRUCTURAL_CRITICAL`은 전시명·시작일·종료일·장소·지역·유효 상태·공식 상세 URL·공식 출처 중 하나 이상의 기관·템플릿 수준 안정적 추출 불가, 핵심 오값 대량 생성 위험 또는 목록-상세 관계 상실이다. 확인 즉시 영향 정본 반영을 막고 `ACTIVE → SUSPENDED`로 전환한다.
- 세 Critical 중 하나가 실행 중 확인되면 영향 기관의 InstitutionRunResult와 전체 IngestionRun은 최종 `FAILED`다. `ACTIVE` 실패 수는 기존 0에서 1 또는 1에서 2로 올리되 중단 판정은 수치를 기다리지 않는다. 실행 밖 정책·구조 검토에서 확인되면 CollectionIssue와 lifecycle·수집 게이트만 갱신하고 가상 IngestionRun·InstitutionRunResult나 실패 수를 만들지 않는다.
- `STRUCTURAL_OPTIONAL`은 요금·예약·관람시간·접근성·감각·미디어만 실패한 경우다. 핵심 대상을 정상 처리했다면 실행은 `SUCCESS`, 값은 `UNKNOWN` 또는 이미지 대체, 기관은 `ACTIVE + DEGRADED`이며 연속 실패 수는 증가하지 않는다.
- `RECORD_EXCEPTION`은 정상 수집·처리한 단일 전시가 핵심 게이트에 실패하지만 기관·템플릿 패턴이 아닌 경우다. 해당 레코드만 정본·파생본·의미 변경 증거에서 격리하고 기관 health·lifecycle·실패 수는 바꾸지 않는다. 같은 핵심 필드·템플릿에서 반복되면 `STRUCTURAL_CRITICAL`로 재분류한다.
- 공유 Source에서도 InstitutionRunResult·health·실패 수·CollectionIssue는 영향 기관별로 분리하고 CollectionIssue의 기본 scope는 `ENTRY`다. Source 전체 정책·접근·구조 문제라는 근거가 있을 때만 `SOURCE`로 넓혀 Source 운영 상태와 연결 기관 전체를 중단한다.
- `PROVISIONAL`에서 Critical이 확인되면 lifecycle은 유지하고 `health = DEGRADED`, `consecutive_final_failed_count = 0`으로 둔 채 미해결 Critical CollectionIssue로 `ACTIVE` 승격과 영향 scope의 추가 수집을 차단한다. 실행 중 확인된 경우 InstitutionRunResult·InstitutionQualificationRun을 최종 `FAILED`로 기록하고 승격 연속 성공을 초기화한다. 실행 밖 검토로 확인된 경우 가상 실패 실행 없이 기존 승격 증거를 무효화한다. 해결 후 수집 게이트가 열려도 승격 검증은 새 시작 시각부터 다시 쌓는다.
- `PROVISIONAL`의 일반 최종 `FAILED`도 health를 `DEGRADED`로 하고 InstitutionQualificationRun의 연속 성공을 초기화하지만 `ACTIVE`용 연속 최종 실패 수는 올리지 않는다. `PROVISIONAL`의 `STRUCTURAL_OPTIONAL`은 `SUCCESS + DEGRADED`, `RECORD_EXCEPTION`은 health 불변으로 판정한다.
